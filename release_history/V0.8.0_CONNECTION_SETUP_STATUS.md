## Concrete staging design to implement after access is restored

Prefer a separate staging project for the shared multi-computer pilot because the existing project contains previous deployments and is named Production. This is a provisional isolation recommendation, not evidence that a new project is mandatory. Finish IAM/resource inspection before choosing; reuse an already-isolated staging project if one exists. Preserve the existing project and data. Do not create a project just because console access failed.

1. **Identity and roles:** Firebase Google sign-in for each tester. Maintain an active-user allowlist and roles on the server. Verify Firebase ID tokens, disabled-user status, and role on every protected request. Never trust the desktop's chosen role, submitted approver name, or an email link as authorization. Confirm employee and approver test identities before assigning access.
2. **Shared data and Q-Codes:** Firestore quotations and revision records. Server allocates staging-only Q-Codes in a transaction, with a unique request key so retries return the same result. Edits carry an expected revision/version and conflicts are reported instead of overwriting another computer's work. Keep live numbering separate until migration is explicitly designed.
3. **Approval service:** A Cloud Run API owns submission and approval transitions. Submission stores a validated immutable revision snapshot, audit event, and notification job atomically. Approval checks role, active status, quotation revision, and pending status in one transaction. Duplicate clicks return the stored result; stale revisions cannot approve. The server recalculates commercial values rather than trusting client totals.
4. **Email and portal:** A hosted HTTPS portal requires sign-in and shows the exact submitted revision. Opening an email link must never approve automatically. A POST action with CSRF protection where cookie authentication is used performs the decision. Replace desktop-local token links with server-owned navigation. Use only confirmed tester recipients during staging; no customer email delivery.
5. **Notification worker:** A private authenticated worker processes the durable outbox with retry/backoff and a lease. Gmail ambiguous-delivery failures must be visible for reconciliation; do not promise exactly-once external email delivery. Submission remains saved if email fails. Mark notifications sent only after provider acknowledgement. Prevent stale revision notifications where possible.
6. **Sender authorization:** Authorize the dedicated Gmail account through Google's user-controlled OAuth consent flow. Keep the refresh credential in Secret Manager and give only the worker access. Do not embed sender refresh credentials or service-account keys in the Windows EXE. Firebase Google sign-in alone does not authorize Gmail sending. Confirm consent-screen state, test users, API enablement, and refresh-token behavior before testing unattended delivery.
7. **Files and configuration:** Private bucket for revision-specific PDFs, with backend-checked access or short-lived download links. Server-owned configuration stores environment, allowed tester recipients, and workflow controls; secrets stay separate. Keep alternate supplier data internal, and build customer PDFs from selected suppliers only. Preserve mandatory final-page terms and low-ink formatting.
8. **Tracker integration:** Queue reporting as a separate operation after the workflow transaction. Do not make a successful approval depend on a synchronous spreadsheet write. Preserve the verified repeated supplier rows, formulas, CO SBM mapping, and retry IDs. Retain the live Tracker write block. Dummy changes require the controlled test setup and must not be run merely to check connectivity.
9. **Logs and audit:** Structured server logs with correlation IDs and secret redaction, centralized append-only business audit events, bounded log retention, alerts for notification/sync failure, and a backup/restore test. Do not copy sensitive quotation bodies or credentials into logs. Protect audit writes through server IAM.
10. **Version management:** Environment-specific API compatibility version and release manifest. Sign the Windows executable/installer and verify update signatures and hashes before installation; support rollback. This is separate from making the approval buttons work and is not implemented by this patch.
11. **Release controls:** Dedicated runtime service accounts with least privilege, private worker ingress, API limits, and separate staging configuration. Review budgets and billing linkage before activating paid services. Cloud costs and alerts are unverified; nothing was enabled here.

Internal Macrotech approval is not customer acceptance. Customer acceptance requires a PO, possibly for only selected items or quantities. Invoicing and payments remain outside this release.

## Required two-button acceptance sequence

| Action | Evidence required |
|---|---|
| Employee signs in | Server identifies the actual user and role |
| Employee clicks Send for approval | One shared revision, one Q-Code allocation, one audit event, and one logical notification job |
| Employee clicks again/retries after timeout | Same submitted revision and Q-Code; no second logical job |
| Approver opens test email on another device | Hosted portal loads the same revision after sign-in |
| Unauthorized account opens link | Access is denied without exposing internal quote data |
| Approver clicks Approved | One server-authorized approval, approver identity/time, and immutable approved revision |
| Another approver clicks simultaneously | Existing result or conflict; no conflicting second approval |
| Employee refreshes on another computer | Same shared approved status and PDF |
| Email provider fails | Submission remains pending, retry state is visible |
| Old revision link is opened | Cannot approve a replaced/recalled revision |
| Customer PO absent | Quotation remains internally approved, not commercially accepted |
